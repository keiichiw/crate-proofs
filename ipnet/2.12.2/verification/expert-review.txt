私なら、**「CIDR が表すアドレス集合を、正しく判定・分割・集約できる」ことを中心に仕様を組みます。** 特に価値が大きいのは、次の4つです。

| 優先したい成果 | 中心となる API | 証明によって利用者が得られる保証 |
|---|---|---|
| 包含判定の正確性 | `contains` | 範囲内の IP・ネットワークを取りこぼさず、範囲外のものを含むと誤判定しない |
| 集約前後の集合の一致 | `aggregate` | CIDR のリストを圧縮しても、対象となる IP が増減しない |
| サブネット分割の正確性 | `subnets`、`*Subnets::next` | 元の範囲を、抜け・重なり・範囲外へのはみ出しなく分割する |
| 列挙と状態更新の正確性 | `hosts`、`*AddrRange` | 前後からの走査やスキップを組み合わせても、返す値と残り範囲が正しい |

実際、ipnet のリリースノートには、**2.12.1 でサブネット列挙が範囲外の最大アドレスを含める問題、2.12.2 で集約が最大アドレスを余計に追加する問題**を修正したとあります。このため、集合の完全一致は、実際に起きた種類のバグを捉えられる仕様です。[Docs.rs](https://docs.rs/crate/ipnet/latest/source/RELEASES.md?utm_source=chatgpt.com)

以下は、公開されている **ipnet 2.12.2** を確認したうえでの具体案です。ご提示のローカルファイルと `theorems.json` はこちらから参照できないため、証明状況は提示された一覧を前提にしています。また、後述する **`schemars` の仕様には、公開実装から具体的な反例が見つかりました。**

## 1. まず、全 API で共有する数学モデルを置く

IPv4 と IPv6 で基本的な仕様を共通化すると、証明を再利用しやすくなります。

ネットワーク `n` について、次を定義します。

- \(w\)：アドレス幅。IPv4 は32、IPv6 は128。
- \(a\)：格納されたアドレスを整数として解釈したもの。
- \(p\)：プレフィックス長。\(0\le p\le w\)。
- \(K=2^{w-p}\)：ネットワーク内のアドレス数。

そのネットワークの先頭・末尾・アドレス集合を、

\[
\operatorname{lo}(n)=\left\lfloor\frac{a}{K}\right\rfloor K
\]

\[
\operatorname{hi}(n)=\operatorname{lo}(n)+K-1
\]

\[
S(n)=\{x\mid \operatorname{lo}(n)\le x\le \operatorname{hi}(n)\}
\]

と定義します。`IpNet` では、集合の要素に IPv4／IPv6 のタグを付け、両者を区別します。

ここで大切なのは、**このモデルを、検証対象の `network()` や `broadcast()` を呼び出して定義しないこと**です。整数の割り算などで独立に定義し、実装がそのモデルと一致することを証明します。

また、ipnet は元のアドレスの host bits を保持します。したがって、次の2つは区別する必要があります。

```text
192.0.2.1/24 と 192.0.2.2/24

Rust の値としては異なる。
表しているアドレス集合は同じ。
```

`trunc()` が、その違いを消してネットワークの先頭アドレスに正規化する操作です。[Rust](https://docs.rs/ipnet/latest/ipnet/struct.Ipv4Net.html?utm_source=chatgpt.com)

**証明の事前条件に「アドレスが既に正規化されている」を置かず、host bits が残っている値も含める**と、実際の API 利用に適用しやすい成果になります。

## 2. `contains`：最初の主成果にしたい仕様

### アドレスに対する包含

証明したいのは、次の同値です。

\[
n.\operatorname{contains}(x)=\mathrm{true}
\iff
x\in S(n)
\]

「含むと判定したら本当に含む」と「本当に含むなら含むと判定する」の両方を証明します。

これによって、たとえば許可 CIDR に基づく判定について、誤った許可と誤った拒否の双方を排除できます。

### ネットワークに対する包含

こちらは、

\[
n.\operatorname{contains}(m)=\mathrm{true}
\iff
S(m)\subseteq S(n)
\]

です。

相手の格納アドレスだけが含まれるという仕様では不十分です。たとえば、

```text
n = 192.0.2.1/24
m = 192.0.2.1/16
```

では、格納アドレスは同じでも、`n.contains(m)` は `false` である必要があります。

### 合わせて欲しい補題

| 性質 | 具体的な仕様 |
|---|---|
| 正規化に依存しない | `contains(n, x) = contains(trunc(n), x)` |
| 反射性 | `n.contains(n) = true` |
| 推移性 | `n.contains(m)` かつ `m.contains(k)` なら `n.contains(k)` |
| 相互包含 | 相互に包含することと、`n.trunc() == m.trunc()` が同値 |
| family の分離 | IPv4 と IPv6 の間の `contains` は `false` |

公開実装にはアドレス用・ネットワーク用の包含判定と、`IpNet` での family 分岐があります。それぞれをこの集合モデルへ対応付けるのがよいです。[Rust](https://docs.rs/ipnet/latest/ipnet/enum.IpNet.html?utm_source=chatgpt.com)

**最初に公開する成果としては、「全プレフィックス・非正規化アドレスを含め、包含判定が CIDR の集合包含と一致する」が、明確で使いやすい主張になります。**

## 3. `aggregate`：最も価値の高い大きな定理

入力リストを \(I\)、集約結果を \(A\) とします。

最優先の仕様は、

\[
\boxed{
\bigcup_{n\in A}S(n)
=
\bigcup_{n\in I}S(n)
}
\]

です。各 IP について書けば、

\[
\forall x,\quad
\left(\exists n\in A,\ x\in S(n)\right)
\iff
\left(\exists n\in I,\ x\in S(n)\right)
\]

となります。

この同値は、**CIDR のリストで表した許可対象・処理対象を、集約によって変更しない**という利用側の保証に直結します。

### 一緒に証明すると強い性質

| 性質 | 仕様 |
|---|---|
| 正規化 | 出力のすべてのネットワークで `n == n.trunc()` |
| 重複・重なりがない | 異なる出力要素のアドレス集合は互いに素 |
| 順序 | 決められた順序で出力される |
| 冪等性 | `aggregate(aggregate(I)) == aggregate(I)` |
| 入力順序に依存しない | 入力を並べ替えても結果が同じ |
| 重複入力に依存しない | 同じネットワークを追加しても結果が変わらない |
| 個数の最小性 | 同じアドレス集合を表す任意の CIDR リストより、出力個数が多くならない |

最初の到達点は集合の一致・正規化・非交差でよいと思います。個数の最小性や正規形の一意性は、その次の目標として自然です。

最小性を証明するときは、各出力 CIDR について、

> その親ネットワーク全体は、入力の和集合には含まれない。

という「これ以上大きくできない」性質を使うと整理しやすくなります。

### 回帰例として必ず含めたい境界

たとえば、全入力を対象にする定理が、次も含んでいることを確認します。

```text
aggregate([255.255.255.254/32])
    = [255.255.255.254/32]
```

`.255` が勝手に加わってはいけません。IPv6 の最大値−1についても同様です。

加えて、空リスト、重複、包含関係のある入力、隣接しているが1つの CIDR にまとめられない入力、IPv4／IPv6 の混在、host bits が残った入力を含めたいです。

### 証明の分け方

公開実装は、おおむねネットワークを区間へ変換し、ソートと区間結合を行い、その後 CIDR へ分解しています。[source](https://docs.rs/ipnet/2.12.2/src/ipnet/ipnet.rs.html?utm_source=chatgpt.com)

したがって、次の補題に分けると進めやすいです。

1. ネットワークから区間への変換が \(S(n)\) を保存する。
2. ソートが区間の集合を保存する。
3. 重なる区間・隣接する区間の結合が和集合を保存する。
4. `Subnets` による CIDR 化が区間を過不足なく覆う。
5. これらを合成して `aggregate` の集合一致を得る。

このうち4が、次の仕様です。

## 4. `subnets` と `*Subnets`：2種類の契約を分ける

### `Net::subnets(q)` は、同じサイズのサブネットへの分割

元のプレフィックスを \(p\) としたとき、まず成功条件を、

\[
\operatorname{subnets}(n,q)\text{ が Ok}
\iff
p\le q\le w
\]

とします。

成功時の出力は、数学的には次の列です。

\[
\text{要素数}=2^{q-p}
\]

\[
\text{第 }i\text{ 要素}
=
\left(
\operatorname{lo}(n)+i\,2^{w-q},\ q
\right)
\qquad
0\le i<2^{q-p}
\]

この仕様により、以下がまとめて得られます。

- 全要素のプレフィックスがちょうど \(q\)。
- 全要素が正規化されている。
- 昇順で、重複や重なりがない。
- 和集合が元の \(S(n)\) に一致する。
- 最後の要素を返した後に終了する。

`q=p` の場合の結果は **`[n.trunc()]`** です。元の `n` に host bits が残っている場合、`[n]` とは異なります。

### `Ipv4Subnets::new(start, end, q)` は、任意の区間の CIDR 分解

こちらの `q` は**最小プレフィックス長**です。出力がすべて `/q` になるとは限りません。公開ドキュメントでも、各ステップで範囲に収まる最大のネットワークを生成すると説明されています。[Rust](https://docs.rs/ipnet/latest/ipnet/struct.Ipv4Subnets.html?utm_source=chatgpt.com)

たとえば、次の範囲なら、

```text
start = 192.0.2.1
end   = 192.0.2.6
q     = 0
```

仕様として期待する分解は、

```text
192.0.2.1/32
192.0.2.2/31
192.0.2.4/31
192.0.2.6/32
```

です。

`next` の1ステップについて、次を証明すると強いです。

> 残り区間の先頭から始まり、残り区間に完全に収まり、プレフィックス長が `q` 以上である最大の CIDR を返す。その CIDR が占める部分を、残り区間から取り除く。

数式では、残り区間を \([s,e]\) として、以下を満たす最大の \(h\) を選びます。

\[
0\le h\le w-q,\qquad
2^h\mid s,\qquad
s+2^h-1\le e
\]

返すネットワークは \((s,w-h)\)、更新後の残り範囲は数学的に \([s+2^h,e]\) です。

この契約から、完全な被覆、非交差、終了、最小個数の分解へ進めます。

### `new` が作れる状態の範囲に注意

**`Ipv4Subnets::new`／`Ipv6Subnets::new` は、プレフィックスを検査せず保存します。** 非空の範囲で `q>w` を指定すると、その後の `next` が内部の `unwrap()` で panic する構造です。[source](https://docs.rs/ipnet/2.12.2/src/ipnet/ipnet.rs.html?utm_source=chatgpt.com)

そのため、契約は次のように分ける必要があります。

| 対象 | 妥当な契約 |
|---|---|
| `Subnets::new` 自身 | 引数を保存した状態を正常に構築する |
| 正常な列挙 | `q≤w` のもとで、正確な CIDR 分解を行う |
| 逆転区間 `start>end` | 空の列として扱う |
| 非空かつ `q>w` | panic に至る挙動を別の仕様として扱う |

「公開コンストラクタで作れる状態だから、後続の `next` もすべて正常終了する」という事前条件の置き方はできません。

## 5. `hosts`・アドレス範囲：返り値と残り状態を一緒に証明する

### `hosts` の具体的な仕様

先頭を \(l=\operatorname{lo}(n)\)、末尾を \(h=\operatorname{hi}(n)\) とすると、列挙対象を次のように定義します。

| 対象 | 列挙するアドレス |
|---|---|
| IPv4、`p<31` | \(l+1\) から \(h-1\) |
| IPv4、`p=31` または `p=32` | \(l\) から \(h\) |
| IPv6 | \(l\) から \(h\) |

つまり IPv4 `/31` は2個、`/32` は1個、IPv6 は範囲の両端を含みます。この違いを含めて仕様化します。[Rust](https://docs.rs/ipnet/latest/ipnet/struct.Ipv4Net.html?utm_source=chatgpt.com)

保証したいのは、その列を**昇順に、各要素をちょうど1回ずつ**列挙することです。

### `AddrRange` 全体を支える状態モデル

イテレータの状態に対し、「まだ消費されていないアドレスの列」\(R\) を対応付けます。`new(a,b)` なら、

\[
R=
\begin{cases}
[a,a+1,\ldots,b] & a\le b\\
[] & a>b
\end{cases}
\]

です。

実際の証明では巨大なリストを生成する必要はなく、空状態または区間で表現できます。

このモデルを使えば、公開 API の仕様を次の表にまとめられます。

| API | 返り値の仕様 | 操作後の残り列 |
|---|---|---|
| `new(a,b)` | 範囲を構築する | 上記の閉区間 |
| `next` | 先頭。空なら `None` | 先頭を1個除く |
| `next_back` | 末尾。空なら `None` | 末尾を1個除く |
| `nth(k)` | 先頭から0始まりで第 `k` 要素。存在しなければ `None` | 先頭から最大 `k+1` 個を消費 |
| `nth_back(k)` | 後ろから0始まりで第 `k` 要素。存在しなければ `None` | 後ろから最大 `k+1` 個を消費 |
| `last` | 非空なら末尾、空なら `None` | `self` を消費 |
| `max` | 非空なら末尾、空なら `None` | `self` を消費 |
| `min` | 非空なら先頭、空なら `None` | `self` を消費 |
| `count` | 長さが `usize` に収まる条件で、正確な長さ | `self` を消費 |
| `size_hint` | 後述する上下限 | 変更しない |

`nth`／`nth_back` では、**返す要素の値だけでなく、飛ばした要素と返した要素を消費すること**が必要です。これは標準 trait の契約にも対応します。[Rust](https://doc.rust-lang.org/std/iter/trait.Iterator.html?utm_source=chatgpt.com)

特に価値がある合成的な性質は、

> `next`、`next_back`、`nth`、`nth_back` を任意の順に呼び出しても、「返した要素」「スキップした要素」「残っている要素」が初期範囲を重複なく分割する。

という保存則です。

### `count` と `size_hint` は別の条件を持つ

残り要素数を \(L\)、`usize::MAX` を \(U\) とします。

`count` の主定理は、

\[
L\le U
\implies
\operatorname{count}(r)\text{ が正常終了し、返り値は }L
\]

です。

一方、`size_hint` には全範囲について、

\[
\operatorname{size\_hint}(r)=
\begin{cases}
(L,\operatorname{Some}(L)) & L\le U\\
(U,\operatorname{None}) & L>U
\end{cases}
\]

という強い仕様を置けます。

公開実装には、この大きさの違いを扱う分岐があり、IPv6 の全範囲については `nth`／`nth_back`／`size_hint` が要素数の `u128` オーバーフローを避けています。`count` の巨大範囲での挙動は、overflow checks の設定も含めて扱う必要があります。[Docs.rs](https://docs.rs/crate/ipnet/latest/source/src/ipext.rs?utm_source=chatgpt.com)

ここは **Lean 側の長さを `Nat` で定義することが必須**です。

- IPv6 全範囲の長さは \(2^{128}\) で、`u128` に収まらない。
- 64 bit ターゲットでも、IPv6 `/64` の長さ \(2^{64}\) は `usize` に収まらない。
- 仕様中の `k+1` も `Nat` で計算し、`k=usize::MAX` を取りこぼさない。

### `FusedIterator`

標準の性質は、

> 一度 `next()` が `None` を返したら、その後の `next()` も常に `None`。

です。[Rust](https://doc.rust-lang.org/std/iter/trait.FusedIterator.html?utm_source=chatgpt.com)

`AddrRange` ではさらに、「どの方向・どのスキップ操作によって空になっても、その後は復活しない」を証明すると有用です。最大アドレスで飽和加算が止まり、同じアドレスを繰り返すような誤りも排除できます。

## 6. マスク・境界・算術：上記の証明を支える正確な仕様

### ネットワークの基礎操作

共通モデルに対して、次の仕様を置きます。

| API | 証明する仕様 |
|---|---|
| `netmask` | 整数値が \(2^w-2^{w-p}\)。上位 `p` bit が1 |
| `hostmask` | 整数値が \(2^{w-p}-1\)。下位 `w-p` bit が1 |
| `network` | 整数値が \(\operatorname{lo}(n)\) |
| `broadcast` | 整数値が \(\operatorname{hi}(n)\) |
| `trunc` | family・prefix を保存し、格納アドレスを \(\operatorname{lo}(n)\) にする。集合保存・冪等 |
| `supernet` | `/0` なら `None`。それ以外は、prefix が1小さい正規化された直近の親 |

`broadcast` は IPv6 でも API 名として存在しますが、ここでは**ネットワーク内の最大アドレス**として仕様化すれば十分です。[Rust](https://docs.rs/ipnet/latest/ipnet/struct.Ipv6Net.html?utm_source=chatgpt.com)

補題としては、

```text
netmask & hostmask = 0
netmask | hostmask = MAX
network ≤ addr ≤ broadcast
S(trunc(n)) = S(n)
trunc(trunc(n)) = trunc(n)
```

が後続の証明に使いやすいです。

### マスクからプレフィックスへの変換

3つの `*_mask_to_prefix` には、次を与えます。

\[
\operatorname{maskToPrefix}(m)=\operatorname{Ok}(p)
\iff
0\le p\le w
\land
m=2^w-2^{w-p}
\]

この仕様は、成功時の値だけでなく、**有効なマスクをすべて受理し、非連続マスクをすべて拒否する**ことを含みます。

具体的には、全0、全1、`255.255.255.0`、`255.0.255.0` のような穴のあるマスクを区別します。公開実装の `leading_ones` とシフトによる検査を、この独立した数式へ結び付けます。[Docs.rs](https://docs.rs/crate/ipnet/latest/source/src/mask.rs?utm_source=chatgpt.com)

`with_netmask` には、成功時に元のアドレスを保存し、変換されたプレフィックスを設定することを与えます。ただし、汎用の `IpNet` 版には次節の注意点があります。

### アドレス拡張 trait

アドレスの整数値を \(\operatorname{val}\)、最大値を \(M=2^w-1\) として、

\[
\operatorname{val}(\operatorname{saturating\_add}(a,d))
=
\min(\operatorname{val}(a)+d,M)
\]

\[
\operatorname{val}(\operatorname{saturating\_sub}(a,d))
=
\max(\operatorname{val}(a)-d,0)
\]

を主定理にします。AND／OR は、幅 `w` の各ビットに対する論理積・論理和との一致です。

戻り値型を区別する必要があります。

| 演算 | 戻り値 |
|---|---|
| アドレス ＋ 整数 | アドレス |
| アドレス − 整数 | アドレス |
| アドレス − アドレス | **`u32` または `u128`** |
| アドレス AND／OR アドレス・整数 | アドレス |

公開実装の各オーバーロードを、同じ数学的仕様へ対応付けます。[Docs.rs](https://docs.rs/crate/ipnet/latest/source/src/ipext.rs?utm_source=chatgpt.com)

合わせて、アドレスと整数の変換がネットワークバイト順の解釈と一致することを証明できると、マスクや範囲の定理につなげやすくなります。

## 7. 名前から想像すると、誤った仕様を置きやすい API

### `is_sibling` は自分自身にも `true` を返す

2.12.2 の実装に対応する仕様は、おおむね、

```text
同じ family
かつ同じ prefix > 0
かつ直近の親ネットワークが同じ
```

です。**異なる子であることは要求していません。** そのため `/0` 以外では `n.is_sibling(&n)` が `true` になります。[source](https://docs.rs/ipnet/2.12.2/src/ipnet/ipnet.rs.html?utm_source=chatgpt.com)

したがって、次の仕様は成立しません。

```text
is_sibling(a, b)
  ⇒ a と b を親ネットワークにまとめても集合が変わらない
```

必要なのは、正規化後にも異なるという条件です。

\[
\operatorname{isSibling}(a,b)
\land
\operatorname{trunc}(a)\ne\operatorname{trunc}(b)
\implies
S(a)\uplus S(b)=S(\operatorname{parent}(a))
\]

単に `a != b` では、`10.0.0.1/24` と `10.0.0.2/24` のような同じ集合を表す値を除外できません。

### `IpNet::with_netmask` は family 不一致を常に拒否するわけではない

公開実装は、マスクからプレフィックス長を取得し、それを元の IP とともに `new` に渡しています。IP とマスクの family の一致は検査していません。[source](https://docs.rs/ipnet/2.12.2/src/ipnet/ipnet.rs.html?utm_source=chatgpt.com)

したがって、実装からは、

```text
IPv6 アドレス ::1
IPv4 マスク 255.255.255.0
    → IPv6 の ::1/24
```

となります。

正確な汎用版の成功条件は、

> マスク自身の family において有効なプレフィックス長 `p` が得られ、かつ、その `p` が元の IP の family にとっても有効である。

です。

「返るネットワークの `netmask()` が入力マスクと等しい」という定理には、同じ family という条件が必要です。この挙動をそのまま契約化するか、API の意図を確認するかは、仕様設計上の判断になります。

## 8. パース・表示・serde：アドレス情報を保存する仕様

### `FromStr`

まず、独立したパース仕様 `ParseSpec` を定義し、

\[
\operatorname{fromStr}(s)=\operatorname{Ok}(n)
\iff
\operatorname{ParseSpec}(s,n)
\]

を目標にします。

段階的には、次の性質が価値を持ちます。

| 性質 | 具体的な内容 |
|---|---|
| 正常終了 | 有限の任意入力について終了し、不正入力は `Err` にする |
| 数値解釈 | IPv4 の各 octet、IPv6 の各 group・省略部分・埋め込み IPv4 を正しい数値へ変換する |
| プレフィックス検査 | IPv4 `/33`、IPv6 `/129` などを拒否する |
| 入力全体の消費 | 有効な CIDR の後ろに garbage が付いた入力を受理しない |
| 情報保存 | 入力の family・アドレス・prefix を保存する。host bits も保存する |
| 文法との一致 | 受理する文字列集合が、定めた文法と一致する |

ここは「どの表記を許すか」を先に明記する必要があります。たとえば公開 parser には IPv4 の先頭ゼロを排除するチェックがないため、**標準ライブラリの parser と入力言語が完全に一致する、と仮定して進めるのは避けたい**です。[Docs.rs](https://docs.rs/crate/ipnet/latest/source/src/parser.rs?utm_source=chatgpt.com)

### `Display`・`Debug`

主定理は、

\[
\operatorname{parse}(\operatorname{display}(n))=\operatorname{Ok}(n)
\]

です。ここでは集合だけでなく、元のアドレスを含む値の完全一致を要求します。

追加するなら、

- 出力はアドレス表記、`/`、10進プレフィックスからなる。
- 同じ表示になる値は等しい。
- 通常の `Debug` 出力が `Display` と一致する。
- 書き込み先が失敗した場合、適切にエラーを返す。

という仕様です。公開実装の表示は格納アドレスを用い、`Debug` は `Display` に委譲しています。[source](https://docs.rs/ipnet/2.12.2/src/ipnet/ipnet.rs.html?utm_source=chatgpt.com)

なお、逆向きの `display(parse(s)) == s` は、IPv6 の省略表記や大文字・小文字などの正規化があるため、要求する仕様ではありません。

### `serde`

人間可読形式とバイナリ形式を分けます。

| モード | 証明したい仕様 |
|---|---|
| 人間可読 | `Display` と同じ文字列を出力し、読込みはパースの意味と一致する |
| IPv4 バイナリ | アドレス4 octet と prefix の5要素 tuple を正しく扱う |
| IPv6 バイナリ | アドレス16 octet と prefix の17要素 tuple を正しく扱う |
| `IpNet` バイナリ | V4／V6 のタグと、対応する値を保存する |

ここでいう tuple は serde のデータモデルです。実際のバイト列は、利用するフォーマットの契約と合成して扱います。公開実装はこの人間可読／バイナリの分岐を持っています。[Rust](https://docs.rs/ipnet/2.12.2/ipnet/?utm_source=chatgpt.com)

特に価値がある追加仕様は、

- serialize→deserialize で family・元のアドレス・prefix が完全に復元される。
- 不正な prefix を持つ入力からネットワーク値を構築しない。
- Serializer／Deserializer の失敗を伝播する。
- 固定長バッファ経路と通常経路の表現が一致する。
- 固定長バッファに表示が必ず収まり、内部の `unwrap()` が失敗しない。

です。2.12.2 の固定長バッファ経路は `ser_as_str` の `cfg` で分岐し、IPv4 は18、IPv6 は43の容量を使用しています。実際の feature 条件に沿って検証対象を記録したいです。[Docs.rs](https://docs.rs/crate/ipnet/latest/source/src/ipnet_serde.rs?utm_source=chatgpt.com)

## 9. `schemars`：すでに反例のある、有用な仕様

この API で最初に欲しいのは、

\[
\boxed{
\forall n,\quad
\operatorname{Validate}
\left(
\operatorname{schema}(T),
\operatorname{serialize}_{JSON}(n)
\right)
=\mathrm{true}
}
\]

です。

つまり、**その型が正常に serialize した JSON を、その型自身の schema が受理する**ことです。

### 2.12.2 の実装では、この性質に反例があります

`schemars08`／`schemars1` の両方で、IPv6 側の正規表現が IPv4 の文字列にも一致します。一方、`IpNet` は IPv4・IPv6 の schema を `oneOf` で組み合わせています。[Docs.rs](https://docs.rs/crate/ipnet/latest/source/src/ipnet_schemars_08.rs?utm_source=chatgpt.com)

ソース中の `type`・`maxLength`・`pattern` の条件を再現して評価すると、次の結果になります。

| 文字列 | IPv4 schema | IPv6 schema | `IpNet` の `oneOf` |
|---|---:|---:|---:|
| `192.168.0.0/24` | 受理 | 受理 | **拒否** |
| `0.0.0.0/0` | 受理 | 受理 | **拒否** |
| `fd00::/32` | 拒否 | 受理 | 受理 |
| `a/64` | 拒否 | 受理 | **受理** |

`oneOf` は「ちょうど1つの枝に一致する」ことを要求するので、2つに一致した正当な IPv4 文字列が拒否されます。[Boolean JSON Schema combination](https://json-schema.org/understanding-json-schema/reference/combining?utm_source=chatgpt.com)

今回確認したのは、公開ソースにある制約そのものの評価で、Rust の schema 生成からの結合テストは実行していません。ただし、上記の不整合は、その制約と `oneOf` の意味から直接説明できます。

仕様は3段階にするとよいです。

1. **出力適合性**：serialize した値は必ず schema に適合する。
2. **受理の健全性**：schema が受理した値は deserialize できる。
3. **受理の完全性**：deserialize できる値は schema も受理する。

まず1を目標にするだけでも、具体的な不具合を捉えられます。**`schema_name` の文字列一致より先に、こちらを検証対象にする価値があります。**

## 10. 変換・derive・エラー型に与える仕様

これらは、主となるモデルへ接続する小さな定理として揃えるとよいです。

| 対象 | 具体的な仕様 |
|---|---|
| `Ipv4Net / Ipv6Net → IpNet` | family・格納アドレス・prefix・表す集合を保存する |
| `IpAddr → IpNet`、具体アドレス→具体ネットワーク | 元アドレスを保存し、prefix が32／128。表す集合が1要素になる |
| 具体 iterator → enum iterator | 変換時点の残り列を保存し、要素に対応する family タグを付ける |
| `Clone` | 値を保存する。iterator では途中まで消費した状態と残り列を保存する |
| `Eq` | 実装されたフィールドの構造的一致と対応する |
| `Ord`・`PartialOrd` | 全順序の法則と `cmp == Equal ⇔ Eq`。必要なら比較キーの正確性も示す |
| `Hash` | 等しい値が、同じ初期状態の hasher に同じハッシュ入力を与える |
| derive の `Debug` | 対象フィールド・variant の表示が正しい。書込みエラーを適切に扱う |
| エラー型 | 正しいエラーが返る、比較・Clone が整合する、表示が適切にエラーを伝播する |

`Default` は独立に値を明示したいです。IPv4 は `0.0.0.0/0`、IPv6 は `::/0`、`IpNet` は IPv4 側がデフォルトです。**空の範囲として使える値ではありません。**[Docs.rs](https://docs.rs/crate/ipnet/latest/source/RELEASES.md?utm_source=chatgpt.com)

`Hash` の衝突がないことや、構造的な `Eq` が集合の等しさと同値であることは要求しません。iterator も、異なる内部状態が同じ空列を表すことがあるため、列の等しさと Rust 値の等しさを分けます。

`new_assert` については、既存の有効プレフィックスでの定理に加え、無効値について実行モデル上の panic に至ることを別の定理にします。これは、const 文脈でのコンパイル時検査とは分けて扱うのが明確です。

## 11. Aeneas での進め方と、最初に目指す到達点

### 定理に「成功すること」と「結果が正しいこと」の両方を含める

Aeneas の公式チュートリアルでも、事前条件のもとで呼出しが成功し、返り値が数式を満たす形式で仕様を書いています。[GitHub](https://github.com/AeneasVerif/aeneas/blob/main/tests/lean/BaseTutorial.lean?utm_source=chatgpt.com)

模式的には、

```text
Pre(input)
  ⇒ 呼出しが成功し、
     Post(input, result, 更新後の状態) を満たす
```

という形です。

`contains` なら成功と判定の同値、`next` なら成功・返す要素・更新後の残り区間まで含めます。マスク変換などでは、Rust の `Err(PrefixLenError)` を正常に返すことと、Aeneas の実行モデルで失敗することも区別します。

### 私なら、この順で進めます

| 順序 | 証明するまとまり | 到達点 |
|---|---|---|
| 1 | アドレス整数対応、算術、マスク変換、境界計算 | 共通の数学モデルとの対応が揃う |
| 2 | `trunc`、`contains`、`supernet`、`is_sibling` | CIDR の正確な包含判定を公開できる |
| 3 | `AddrRange` の状態遷移と `hosts` | 端点・前後走査・スキップを含む列挙の正確性を示せる |
| 4 | `Subnets` の区間分割と `aggregate` | 分割・集約による対象アドレス集合の保存を示せる |
| 5 | `FromStr`、表示、serde | 入力・保存・再読込みでアドレス情報を保存できる |
| 随時 | 変換、derive、エラー型 | 各成果を公開 API 全体へ接続する |

`schemars` の反例は、この順序とは別に、早い段階で不整合として扱う価値があります。

ネットワーク算術の抽出が詰まっている間も、数学モデルと補題の整備、抽出できる API の証明は進められます。ただし、**手で書いた数学モデルの証明と、抽出された ipnet 実装がそのモデルを満たす証明は、成果として区別する**必要があります。未検証 API ごとの抽出可否は個別に確認し、同じ障害があると一括して扱わない方針がよいです。

最初の公開成果には、次の主張を勧めます。

> **IPv4／IPv6 の全プレフィックスと、host bits を含む格納アドレスについて、`contains` が数学的な CIDR 包含と一致する。**

その次の主成果として、

> **サブネット分割とネットワーク集約が、対象アドレスを追加・欠落させず、元のアドレス集合を正確に保存する。**

を目指すのがよいと思います。この2つは、proofs.rs を読む利用者が「自分のコードのどの判断に、この証明を使えるか」を具体的に理解できる仕様です。
