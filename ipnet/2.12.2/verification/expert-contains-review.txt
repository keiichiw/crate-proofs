**はい。次の到達点は `contains` の完成に置くのが適切です。** すでに `network`・`broadcast` と独立モデルの対応があるため、残る比較の橋渡しを閉じれば、「公開 API の判定が、CIDR の表す集合への所属・包含と一致する」という一まとまりの保証が得られます。この比較の証明は、後続のイテレータの終端判定にも使えます。

進め方としては、**まず IPv4 の `contains` を独立して完成させ、IPv6 の `segments()` 対応を並行して進める**ことを勧めます。その後は、範囲イテレータの一歩の証明を確立し、サブネット分割と集約へ進みます。`AddrRange` の全メソッドを完成させることを、集約の前提にする必要はありません。

以下では、既存の119定理はご報告どおり利用できるものとして、追加すべき契約と完了条件を具体化します。

## 1. 抽出障害は、どの範囲で解消するべきか

### 1.1 推奨する選択順

標準ライブラリの実装抽出と外部モデルの選択は、次の順に判断するとよいです。

| 状況 | 推奨する対応 | 完了時に説明できること |
|---|---|---|
| 既存の対応があり、型・名前・登録先だけが食い違っている | 生成処理やモデル接続の不整合を修正する | 元の操作の意味を保ったまま、抽出経路がつながった |
| 必要な標準ライブラリ関数を、小さな依存範囲で抽出できる | その関数を抽出し、生成された関数について証明する | 既存の変換基盤の信頼範囲内で、比較の実装まで検証できた |
| 抽出すると、今回に不要な unsafe 操作などへ対応範囲が広がる | 小さな関数・具体的な型に限定して外部モデルを設ける | モデルとの対応を証明した部分と、信頼している部分を区別して保証できる |

**IPv4 の配列／スライス問題は、まず一段目を調べるべきです。** 型不一致という情報だけから、比較の意味そのものを新しくモデル化する必要があるとは判断できません。

最小再現例では、少なくとも次を対応づけます。

- 元の Rust の具体的な呼出先。
- Charon が出した LLBC の型と trait 呼出。
- 生成 Lean の引数型・戻り値型。
- 適用された標準ライブラリモデルと、その登録先。
- 配列からスライスへの変換が入る位置。

例えば、`[u8; 4]` の比較、`Ipv4Addr` の `<=`、`Ipv6Addr::segments()`、`Ipv6Addr` の `<=` をそれぞれ最小例に分けます。固定した Rust・Charon・Aeneas・Lean、target、機能フラグは、既存の検証設定をそのまま添付すれば十分です。

今回確認した公開 Rust ソースでは、IPv4 の比較は octet 配列、IPv6 の比較は `segments()` の配列を経由します。ただし、最終的な修正対象は、ご使用の固定 toolchain のソースと実際の抽出結果から確定してください。[source](https://doc.rust-lang.org/src/core/net/ip_addr.rs.html?utm_source=chatgpt.com)

### 1.2 外部モデルでは「正当化」の種類を分ける

ここは今後の報告でも明確にしておくとよい点です。

**追加の Lean 公理がないことは、Rust 実装と手書きモデルの対応が証明されたことまでは意味しません。**

例えば、Lean で比較モデルを自然数比較として `def` し、その性質を追加公理なしで証明することはできます。しかし、その定義を Rust の比較関数へ割り当てる対応関係は、別の根拠を必要とします。Aeneas 開発者の解説でも、外部関数へ手書きの本体を与える方法は、明示的に *trusted model* と説明されています。[Jonathan Protzenko](https://jonathan.protzenko.fr/2026/05/05/jxl-rs.html?utm_source=chatgpt.com)

したがって、外部モデルは次のように分類するのを勧めます。

| モデルの位置づけ | 必要な記録 |
|---|---|
| 元の抽出済み関数との等価性を Lean で証明した補助モデル | 等価性定理と、その依存関係 |
| 特定のプリミティブについて、既存の形式的意味論から対応を証明したモデル | 適用対象、意味論、対応定理 |
| Rust 実装との一致をレビューによって信頼するモデル | 対象シンボル、型の特殊化、固定バージョン、未証明の対応関係 |

三番目も、境界が小さく明示されていれば実用的な選択肢です。その場合は、`contains` の保証を「この標準ライブラリモデルとの対応を前提にした保証」として記録します。

私なら、**同程度の作業量で済むなら実装抽出を選び、対応範囲が大きく広がる場合は、小さな外部モデルへ境界を移します。** 今回、汎用的な `transmute<T, U>` の支援まで先に完成させる必要はありません。

## 2. 比較の橋渡しに要求する補題と観測

ご質問の「辞書式順序と自然数順序の一致」は数学的な中心です。ただし、公開 API の検証を完成させるには、その前後を含めた次の四層が必要です。

### 2.1 配列からスライスへの変換が、比較対象を保存する

元の配列を \(a:[T;N]\)、比較へ渡すスライスを \(s\) として、要求する契約は次です。

\[
\operatorname{length}(s)=N
\]

\[
\forall i<N,\quad s[i]=a[i]
\]

これに加えて、共有借用として観測する元の値が変わらないことを確認します。現行 Rust の配列比較は、スライスへの変換と参照の比較を経由しているため、この接続を明示すると型不一致の修正をレビューしやすくなります。[source](https://doc.rust-lang.org/src/core/array/mod.rs.html?utm_source=chatgpt.com)

この段階の目標は、単に Lean の型検査を通すことだけではありません。**変換後に比較する長さ・要素・要素順が、元の配列と一致すること**までを一つの契約にします。

### 2.2 固定長の桁列について、返る `Ordering` 全体を一致させる

既存モデルに合わせて、上位桁から並んだ列の値を

\[
V_B(d_0,\ldots,d_{N-1})
=
\sum_{i=0}^{N-1} d_i B^{N-1-i}
\]

とします。

中心となる補題は、次の形がよいです。

\[
\operatorname{lexCmp}(x,y)
=
\operatorname{Nat.compare}(V_B(x),V_B(y))
\]

前提は、

\[
B\ge 2,\qquad
\operatorname{length}(x)=\operatorname{length}(y)=N
\]

\[
\forall i<N,\quad 0\le x_i,y_i<B
\]

です。

特殊化は、まず次の二つで足ります。

| 用途 | 底 \(B\) | 長さ \(N\) |
|---|---:|---:|
| IPv4 の octet 比較 | 256 | 4 |
| IPv6 の segment 比較 | 65536 | 8 |

`Less` の片方向だけを証明するより、**`Less`・`Equal`・`Greater` の結果全体を一致させる**方が、その後の `<=`、終端判定、`min`・`max` に使いやすくなります。

見落としやすい条件は、等長性と桁の上限です。

- 等長性を外すと、`[1] >lex [0,2]` ですが、底256の数値としては \(1<2\) です。
- 桁に256を許すと、`[0,256] <lex [1,0]` ですが、両方の数値は256です。

証明の中心は「最初に異なる上位桁の差を、下位桁全体では覆せない」という補題です。残りが \(k\) 桁なら、その値は \(B^k\) 未満です。この補題を一度作れば、IPv4 と IPv6 へ共通に適用できます。

なお、実際のスライス比較には特殊化があります。例えば現行ソースの `u8` 比較には `compare_bytes` を使う経路があります。固定 toolchain が選んだ経路を確認し、そこへ辞書順の契約を接続してください。[source](https://doc.rust-lang.org/src/core/slice/cmp.rs.html?utm_source=chatgpt.com)

### 2.3 IPv6 は `segments()` 全体と、生の `transmute` を区別する

byte 列を \(b_0,\ldots,b_{15}\) としたとき、`segments()` 全体に要求する契約は、

\[
\forall i<8,\quad
s_i=256b_{2i}+b_{2i+1}
\]

です。その上で、

\[
V_{65536}(s_0,\ldots,s_7)
=
V_{256}(b_0,\ldots,b_{15})
=
\operatorname{addrNat}(a)
\]

という桁の組み替えの補題を示します。

**ここで特に注意したいのは、`transmute` の直後に `u16::from_be` があることです。** 確認した Rust ソースは、まず16バイトを8個の `u16` に値として transmute し、その各要素へ `from_be` を適用しています。[source](https://doc.rust-lang.org/src/core/net/ip_addr.rs.html?utm_source=chatgpt.com)

生の transmute の結果 \(t_i\) は、target の endian に応じて、

\[
t_i=
\begin{cases}
256b_{2i}+b_{2i+1} & \text{big-endian}\\
b_{2i}+256b_{2i+1} & \text{little-endian}
\end{cases}
\]

となります。その後の `from_be` と合成して初めて、両環境で目的の

\[
256b_{2i}+b_{2i+1}
\]

になります。

したがって、モデルを設ける位置は次のどちらかです。

1. **生の transmute に native endian の意味を与え、抽出された `from_be` と合成する。**
2. **`segments()` 全体を境界にして、big-endian の二桁結合という契約を与える。**

生の transmute だけを最初から big-endian の結合に置き換え、後続の `from_be` を残すと、little-endian 環境で二重変換になります。

この限定的な transmute の確認事項は、サイズがともに16バイト、要素配置、初期化された全ビットの保持、整数の値としての妥当性、endian です。これは値としての transmute なので、参照キャストのように両型の alignment が同じであることを要求する必要はありません。Rust の説明でも、この違いは区別されています。[Rust](https://doc.rust-lang.org/std/mem/fn.transmute.html?utm_source=chatgpt.com)

### 2.4 実際に呼ばれる比較関数まで接続する

数学的な比較補題の次に、**抽出された関数そのもの**について、次の契約を置きます。ここで \(\Downarrow\) は、正常に終了して指定した結果を返すことを表す説明用の記法です。

\[
\operatorname{cmp}(a,b)
\Downarrow
\operatorname{Nat.compare}(\operatorname{addrNat}(a),\operatorname{addrNat}(b))
\]

\[
\operatorname{partialCmp}(a,b)
\Downarrow
\operatorname{Some}
\left(
\operatorname{Nat.compare}(\operatorname{addrNat}(a),\operatorname{addrNat}(b))
\right)
\]

\[
\operatorname{le}(a,b)
\Downarrow
\operatorname{decide}
\left(
\operatorname{addrNat}(a)\le\operatorname{addrNat}(b)
\right)
\]

要求する観測は、次のとおりです。

- 正確な返り値。
- `partial_cmp` が `None` を返さないこと。
- 実際に現れる添字アクセス・変換等が失敗しないこと。
- 入力や、抽出シグネチャに現れる返却状態が保存されること。
- trait の宣言だけでなく、実際の呼出先との接続。

`contains` に直接必要なのは `<=` です。呼出経路上で必要になる `cmp`・`partial_cmp` を証明し、未使用の比較メソッドをすべて先に終える必要はありません。後の `Subnets::next` で実際に使う `eq` などは、その段階で同じ方針で接続できます。

### 2.5 `contains` の完了条件

同一 family の有効なネットワークについて、目標は次の二種類です。

**アドレス包含**

\[
\operatorname{contains}(n,a)\Downarrow b
\quad\land\quad
\left(
b=\mathrm{true}
\iff
lo(n)\le\operatorname{addrNat}(a)\le hi(n)
\right)
\]

**ネットワーク包含**

\[
\operatorname{contains}(n,m)\Downarrow b
\quad\land\quad
\left(
b=\mathrm{true}
\iff
lo(n)\le lo(m)\land hi(m)\le hi(n)
\right)
\]

既存の集合包含補題によって、後者を \(S(m)\subseteq S(n)\) と結びます。

`ipnet 2.12.2` では、IPv4／IPv6 のアドレス包含・ネットワーク包含の四つと、`IpNet` の二つの分岐実装を対象にします。異なる family の場合は `false` です。公開の generic `contains<T>` についても、組込みの型への特殊化がこれらの実装へ到達することを接続します。[source](https://docs.rs/ipnet/2.12.2/src/ipnet/ipnet.rs.html?utm_source=chatgpt.com)

**ここを最初の完了単位にしてください。**

- 四つの具体的な包含実装。
- 二つの `IpNet` 実装と family の分岐。
- 対応する公開メソッドへの接続。
- 全有効プレフィックスと非正規化入力。
- 正常終了と判定値の同値。
- 使用した外部モデルの対応根拠の記録。

なお、相互包含から直ちにネットワーク型の生の値の等号を導かないようにします。例えば `10.0.0.1/24` と `10.0.0.2/24` は同じ集合を表しますが、格納されたアドレスは異なります。

## 3. その後の証明単位は、実装の依存に合わせて切る

実際の依存を整理すると、次の三つの経路になります。

| 目的 | 証明を接続する経路 |
|---|---|
| アドレスの列挙・`hosts` | ネットワーク端点 → `AddrRange` の状態遷移 |
| サブネット分割 | 端点・整数演算 → 次の CIDR を選ぶ helper → `Subnets::next` |
| 集約 | 端点 → 区間のソート → 区間の併合 → `Subnets` による CIDR 化 |

`aggregate` は `AddrRange` を使わず、区間をソート・併合した後、`Subnets::new(..., 0)` を用いて CIDR に戻します。したがって、**Range の `count`・`nth` などは、集約へ進む作業と分けられます。**[source](https://docs.rs/ipnet/2.12.2/src/ipnet/ipnet.rs.html?utm_source=chatgpt.com)

### 3.1 最初の状態付き証明は `Ipv4AddrRange::next` 一つにする

ここでは、新しく複雑な列のモデルを作るより、**残っている半開区間**をモデルにするのがよいです。

生の端点を自然数化した値を \(s,e\) として、

\[
\mathcal R(r)=
\begin{cases}
\mathrm{Empty} & s>e\\
\mathrm{Live}(s,e+1) & s\le e
\end{cases}
\]

とします。

`Live(s,t)` は \([s,t)\) を表し、

\[
0\le s<t\le 2^w
\]

を満たすものとします。端点・残長はすべて Lean の `Nat` に置きます。これなら IPv6 の全範囲も `Live(0,2^128)` と表せます。

証明済みの生コンストラクタには、格納値保存からこの初期状態へ接続する補題だけを足せば十分です。

`next` の契約は次です。

| 実行前の状態 | 返り値 | 実行後の残り |
|---|---|---|
| `Empty` | `None` | `Empty` |
| `Live(s,t)`、\(s+1=t\) | 値 \(s\) のアドレス | `Empty` |
| `Live(s,t)`、\(s+1<t\) | 値 \(s\) のアドレス | `Live(s+1,t)` |

**この一つの定理で、正常終了・返り値・更新後状態を合わせて証明します。**

完了条件には、逆転した端点、0だけの範囲、最大アドレスだけの範囲、全範囲を含めます。空状態の具体的な番兵表現は抽象化してよいので、空の生状態どうしが完全に同じフィールド値になることまでは要求しません。

この定理が完成したら、同じモデルで `next_back` を追加します。非空なら \(t-1\) を返し、残りは \([s,t-1)\) です。

その二つから、任意の前後操作列について、

- 残り区間が正確に維持される。
- 一度返した要素を再び返さない。
- 空になった後は、どちらからも要素が復活しない。

という性質を導けます。`FusedIterator` の性質も、この空状態の保存から系として出します。

### 3.2 Range の残りは「スキップ」と「観測」に分ける

残長を \(L=t-s\)、引数 `n` の自然数値を \(k\) とすると、スキップ操作の契約は次です。

| 操作 | \(k<L\) | \(k\ge L\) |
|---|---|---|
| `nth(n)` | \(s+k\) を返し、残りは \([s+k+1,t)\) | `None`、残りは空 |
| `nth_back(n)` | \(t-1-k\) を返し、残りは \([s,t-1-k)\) | `None`、残りは空 |

長さ0の区間は `Empty` と読み替えます。仕様中の \(k+1\) は `Nat` で計算し、`usize` の加算として書かないことが大切です。

この単位の完了条件は、返り値だけでなく、**飛ばした要素も消費されること**と、範囲外の `nth` の後も空が維持されることです。`nth(0)` と `next` の一致も、返り値と残り状態の両方について示せます。

観測メソッドは、target の `usize::MAX` を \(U\) として、次の契約にします。

\[
\operatorname{sizeHint}(r)=
\begin{cases}
(L,\operatorname{Some}(L)) & L\le U\\
(U,\operatorname{None}) & L>U
\end{cases}
\]

\[
L\le U
\Longrightarrow
\operatorname{count}(r)\Downarrow L
\]

`last`・`max` は非空なら \(t-1\)、`min` は非空なら \(s\)、空ならいずれも `None` です。

**`count` の正常終了には表現可能性の前提を付け、`size_hint` は巨大範囲も対象にします。** 公開実装でも、巨大なカウントを扱う分岐とオーバーフローし得る処理は区別されています。\(L>U\) の panic・overflow 挙動まで扱う場合は、ビルド設定を固定した別の契約にします。[Docs.rs](https://docs.rs/crate/ipnet/latest/source/src/ipext.rs?utm_source=chatgpt.com)

### 3.3 サブネットは、まず「一区画が正しく収まる」ことを証明する

次の単位は `next_ipv4_subnet`／`next_ipv6_subnet` です。

前提を、

\[
0\le s\le e<2^w,\qquad 0\le q\le w
\]

とします。\(q\) は `min_prefix_len` です。

返されたネットワークを \(C\)、プレフィックスを \(p_C\)、サイズを \(d=2^{w-p_C}\) として、まず要求するのは次です。

\[
q\le p_C\le w
\]

\[
\operatorname{addrNat}(C.addr)=lo(C)=s
\]

\[
1\le d,\qquad s+d\le e+1
\]

\[
S(C)=[s,s+d)
\]

これに正常終了を加えます。

これで、「残っている範囲の先頭から、正規化された非空の CIDR を一つ切り出す」という契約になります。内部のビットカウント演算については、この契約に必要な意味だけを先に接続します。

**最初の段階では、最大サイズの CIDR を選ぶことまで要求しなくて構いません。** 完全な被覆と停止性には、正しい開始位置・範囲内に収まること・正のサイズがあれば先へ進めます。

最大性は、次の別定理にします。任意の候補プレフィックス \(r\) について、

\[
q\le r\le w,\qquad
2^{w-r}\mid s,\qquad
2^{w-r}\le e+1-s
\]

なら、

\[
p_C\le r
\]

です。プレフィックスが小さいほどブロックが大きいので、これが「選べる最大のブロック」という意味になります。

### 3.4 `Subnets::next` は、出力と残りの完全な分割を証明する

Subnets にも `Empty`／`Live(s,t)` の残り区間モデルを使い、追加で \(q\) を保持します。

非空状態に対する一歩の契約は、

- `Some(C)` を返す。
- \(S(C)=[s,u)\)、かつ \(s<u\le t\)。
- 残りは \([u,t)\)。
- \(q\) は変わらない。

です。

中心となる保存則は、

\[
\mathcal R(r)
=
S(C)\;\dot\cup\;\mathcal R(r')
\]

です。\(\dot\cup\) は、互いに重ならない和を表します。

停止性の尺度は、自然数で表した残長にします。

\[
\mu(r)=
\begin{cases}
0 & \mathrm{Empty}\\
t-s & \mathrm{Live}(s,t)
\end{cases}
\]

`Some(C)` を返すたびに、

\[
\mu(r')=\mu(r)-|S(C)|<\mu(r)
\]

を示します。

実装では最大アドレス付近に飽和演算と終端処理があるため、生の `start` が増えることだけに停止性を依存させない方が扱いやすくなります。[source](https://docs.rs/ipnet/2.12.2/src/ipnet/ipnet.rs.html?utm_source=chatgpt.com)

ここで、**生コンストラクタの証明から、\(q\le w\) を自動的に導いてはいけません。** 任意の引数を格納できることと、その後の反復が正常終了することは別です。

契約の適用範囲は、例えば

\[
\mathcal R(r)=\mathrm{Empty}\ \lor\ q\le w
\]

とできます。空なら `None` を返す契約、非空なら有効な \(q\) の下で一歩進む契約です。

この単位の完了条件は、次の五つです。

1. `None` を返すことと、残りが空であることの同値。
2. 出力と更新後の残りによる厳密な分割。
3. 出力の正規化とプレフィックス制約。
4. `Some` ごとの残長の厳減。
5. 最大アドレスを含む最後のブロックの後も空になること。

### 3.5 全体の分割と、公開 `subnets` を接続する

一歩の定理ができれば、残長に関する帰納法で、出力列 \(C_0,\ldots,C_{m-1}\) に対して、

\[
\bigcup_{i<m}S(C_i)=[s,t)
\]

を導けます。加えて、相互非重複、昇順、正規化、有限回での終端、終端後の空の保存を示します。

公開 `Net::subnets(q)` には、さらに次の契約を与えます。元のプレフィックスを \(p\) として、

- \(p\le q\le w\) なら、有効な反復状態を返す。
- \(q<p\) または \(q>w\) なら、通常の `PrefixLenError` を返す。
- 有効な場合、すべての出力のプレフィックスは**ちょうど** \(q\)。

最後の「ちょうど \(q\)」は、先ほどの弱い「\(q\) 以上で収まる」契約だけからは出ません。**整列した区間では helper がプレフィックス \(q\) を返す、という特殊化した補題を追加する**か、最大性の定理を使います。

その上で、

\[
D=2^{w-q},\qquad m=2^{q-p}
\]

\[
C_i=(lo(N)+iD)/q
\qquad(0\le i<m)
\]

という、要素数と各要素の正確な式まで証明できます。

ここでの全列挙は、`next` の呼出列についての数学的な保証です。**Rust の `collect::<Vec<_>>()` の正常終了まで自動的に証明されたことにはなりません。** 例えば数学的な要素数が \(2^{128}\) となる場合にも、イテレータの契約とコンテナへの収集の契約は分けて扱います。

## 4. `aggregate` は、ソート・併合・CIDR化の三段階にする

### 4.1 ソートには順序と要素保存の両方を要求する

各ネットワークを、

\[
I_i=[lo(N_i),hi(N_i)+1)
\]

へ写す処理を既存の端点定理につなげます。ここでも、入力の正規化を前提に加える必要はありません。

`sort_unstable` に必要な契約は、

\[
\operatorname{Perm}(I,I')
\]

と、

\[
\operatorname{SortedByStart}(I')
\]

です。実装の tuple の辞書順は、開始点の非減少順を得るのに使えます。

**順序だけでは足りません。要素が消えたり増えたりしないことも必要です。**

Rust のソート実装そのものを検証対象にするなら、独立した大きな作業になります。外部契約として扱うなら、その二条件と正常実行を信頼する境界として記録し、まずその下で ipnet の集約処理を証明するのが現実的です。

### 4.2 併合ループでは、処理済み入力の和集合を不変条件にする

処理済みの入力区間を \(P\)、累積した区間列を \(M\) とします。

ループ不変条件は、次の組合せがよいです。

- \(M\) の各区間は非空で有効。
- \(M\) は開始点の昇順。
- 連続する区間には、重複も隣接も残っていない。
- \(\bigcup M=\bigcup P\)。
- 未処理入力は、ソート済みの順序に従っている。

これによって、次の区間と併合できるかを最後の区間だけで判断できることを示します。

飽和加算については、\(M_w=2^w-1\)、\(s\le M_w\) の下で、

\[
s\le\min(e+1,M_w)
\iff
s\le e+1
\]

を使うと、実装の隣接判定と自然数上の判定を接続できます。

Aeneas では、`last_mut` で借りた終端値を更新した後、**更新が返却される `Vec` 全体へ反映されること**まで確認します。借用先の値だけについて和集合保存を示しても、外側の状態との接続はまだ残ります。

停止尺度は、未処理の入力区間数です。各反復で一つ減るため、アドレス値や区間の幅を使う必要はありません。

### 4.3 CIDR化の処理へ `Subnets` の定理を接続する

併合後の区間それぞれについて、完成した `Subnets::new(start,end,0)` の被覆定理を使います。

累積した出力を `res`、CIDR 化済みの区間列を `done` として、

\[
\bigcup_{C\in res}S(C)
=
\bigcup done
\]

を不変条件にします。

ここで実際に使われる `Vec::extend` などにも、列挙される要素を過不足なく追加する契約を接続します。**Subnets の数学的な反復定理と、抽出された `extend` の呼出がつながったところまでが、`aggregate` の証明範囲です。**

最初の公開成果は、正常終了に加えて、

\[
\forall x,\quad
x\in\bigcup_{C\in\operatorname{aggregate}(Ns)}S(C)
\iff
x\in\bigcup_{N\in Ns}S(N)
\]

とします。

その時点で合わせて要求したいのは、出力の正規化、相互非重複、各 family 内の昇順です。`IpNet` については、family ごとの振り分けと結合がタグ付き集合を保存することを追加します。

この段階だけでも、「集約によって対象アドレスが増えず、失われもしない」という重要な保証になります。

### 4.4 最小個数・一意性は次の到達点にする

集合和保存の後で、helper の最大性を用いて、

> 出力は、その集合に含まれる極大な CIDR ブロックを順に並べたものである。

という特徴づけを目指します。

CIDR の包含関係の木構造を使い、この特徴づけから、最小個数、入力順序や重複に対する結果の不変性、冪等性を導く方針がよいです。

`min_prefix_len=q>0` の一般的な分割では、極大性にも「親のプレフィックスが \(q\) 以上」という制約が入ります。`aggregate` は \(q=0\) なので、その制約のない形へ特殊化できます。

## 5. Astra と Sol の次の受け渡しをどう切るか

最初の受け渡しは、次の三件に分けることを勧めます。

| 作業単位 | Astra が先に固定するもの | Sol 側の完了条件 |
|---|---|---|
| IPv4 の比較と包含 | 配列／スライス保存、数値順との一致、二種類の包含契約 | 実際の比較経路と二つの `contains` が正常終了・同値まで通る |
| IPv6 の変換・比較と包含 | segment の式、endian の扱い、モデル境界 | 実際の `segments`／比較経路から二つの `contains` まで接続できる |
| 公開 API への統合 | family の意味、対象とする型の特殊化 | `IpNet` の二実装と公開 wrapper が接続され、既存の監査を通る |

レビュー時の成果物には、定理一覧に加えて、**新規の外部モデルについて「対応を証明したか、信頼しているか」が分かる対応表**を一つ加えるとよいです。これで、公理監査だけでは見えない変化を追えます。

有限テストは、すでにあるものを利用し、新しい接続点に絞って確認すれば十分です。比較では例えば、

- `1.0.0.0 > 0.255.255.255`
- `00ff:ffff:ffff:ffff:ffff:ffff:ffff:ffff < 0100::`
- bytes `[01,02,03,04,…,0f,10]` から segments `[0102,0304,…,0f10]`
- 非正規化した `10.0.0.1/24` の端点包含

が、桁順・endian・公開 API への接続の取り違えを見つけやすい例です。全ゼロや全 `ff` だけでは byte swap の誤りを検出できません。

次の状態付き証明のレビューでは、`Ipv4AddrRange::next` 一つを対象に、**返ったアドレスと更新後の残り区間が、同じ定理で特定されていること**を確認してください。その書き方が確立したら、Range の追加メソッドと、`Subnets` から `aggregate` へ進む作業を分けて進められます。
